# Investigation: Pgembed + tigerfs + psql_bm25s as Virtual Filesystem

> **[Superseded] pg_duckdb has since been removed from pgembed.** This investigation is a dated historical record; its statements about the `pg_duckdb` entry in pgembed's extension registry no longer reflect the current codebase.

## Summary
可以用 TigerFS 挂载 Pgembed 启动的 PostgreSQL 数据库，但前提是 Pgembed server 持续运行，并把 `PostgresServer.get_uri()` 返回的 socket/TCP 连接串显式传给 TigerFS。`psql_bm25s` 可以在底层 PostgreSQL 中作为扩展/索引访问方法工作，但不会自动变成 TigerFS 的文件系统级搜索能力；当前 TigerFS 默认路径生成的是等值过滤、普通排序和 `SELECT *`，不会调用 `psql_bm25s_query*`、`@@`、`@@@` 或 `<=>`。

## Symptoms
- User asks whether Pgembed can be mounted as a virtual filesystem using tigerfs.
- User asks whether the `psql_bm25s` PostgreSQL extension can work in that filesystem background/context.

## Background / Prior Research

### tigerfs PostgreSQL connection and privilege model
- TigerFS is intended to mount arbitrary reachable PostgreSQL databases by connection string. Its README states that TigerFS works with any PostgreSQL database and shows `tigerfs mount postgres://user:pass@host/mydb /mnt/db` (`tigerfs/README.md:269-276`).
- TigerFS implementation uses `pgx/v5` and `pgxpool`, not `lib/pq`; connection strings are parsed via `pgxpool.ParseConfig(connStr)` (`tigerfs/go.mod:9`, `tigerfs/internal/tigerfs/db/client.go:83-91`).
- pgembed appears plausible as a tigerfs backend if the embedded PostgreSQL server is already running and TigerFS receives a pgx-compatible URI. On Unix-like systems pgembed uses a Unix socket (`-h ""`, `-k <socket_dir>`), and `get_uri()` returns a socket URI like `postgresql://postgres:@/postgres?host=/path/to/socketdir` (`pgembed/src/pgembed/postgres_server.py:196-211`, `pgembed/src/pgembed/utils.py:88-98`). On Windows it uses `127.0.0.1:<port>` (`pgembed/src/pgembed/postgres_server.py:212-221`).
- TigerFS discovers schemas/tables via `information_schema` and `pg_catalog`, maps filesystem operations to ordinary PostgreSQL privileges, and checks privileges with `has_table_privilege()` (`tigerfs/internal/tigerfs/db/schema.go:44-103`, `tigerfs/internal/tigerfs/db/permissions.go:10-80`, `tigerfs/internal/tigerfs/db/permissions.go:136-143`).
- Primary keys matter for normal row-as-file access (`tigerfs/docs/data-first.md:7-12`, `tigerfs/internal/tigerfs/db/keys.go:24-29`). File-first/build/history features may need DDL rights and use a dedicated `tigerfs` schema (`tigerfs/CHANGELOG.md:10-16`, `tigerfs/internal/tigerfs/fs/synth/build.go:9-13`, `tigerfs/internal/tigerfs/fs/synth/build.go:238-263`).

### psql_bm25s PostgreSQL extension semantics
- `psql_bm25s` is a native PostgreSQL index access method extension, not a filesystem/VFS/FUSE layer. Its SQL defines `CREATE ACCESS METHOD psql_bm25s TYPE INDEX HANDLER psql_bm25s_handler;` (`psql_bm25s/sql/psql_bm25s--0.4.14.sql:1-75`).
- Basic installation is normal PostgreSQL extension installation followed by `CREATE EXTENSION psql_bm25s;` (`psql_bm25s/README.md:184-218`, `psql_bm25s/docs/contribution.md:7-34`). The control file uses `$libdir/psql_bm25s`, default version `0.4.14`, and is not relocatable (`psql_bm25s/psql_bm25s.control`).
- User indexes are defined with SQL such as `CREATE INDEX docs_bm25_idx ON docs USING psql_bm25s (body);` (`psql_bm25s/README.md:233-263`, `psql_bm25s/docs/index-parameters.md:1-16`). Supported indexed input types include `int4[]`, `text[]`, `varchar[]`, `text`, and `varchar` (`psql_bm25s/docs/input-types.md:1-15`).
- Queries use SQL functions/operators such as `psql_bm25s_query_ids(...)`, `psql_bm25s_query_tokens(...)`, `@@`, `@@@`, and `<=>` (`psql_bm25s/docs/query-semantics.md:1-24`, `psql_bm25s/docs/api-reference.md:1-33`, `psql_bm25s/docs/api-reference.md:218-248`). True BM25 ordering through `<=>` depends on PostgreSQL using a real `psql_bm25s` index scan.
- Basic use does not require `shared_preload_libraries`; preload is optional/recommended for shared generation cache and background maintenance (`psql_bm25s/docs/connection-memory.md:55-80`, `psql_bm25s/docs/index-parameters.md:118-151`). Current documented release targets are PostgreSQL 17 and 18 (`psql_bm25s/docs/contribution.md:52-64`).

## Investigator Findings

### 2026-05-15 - Cross-repo verification

#### 1. Pgembed lifecycle, URI/socket, and extension activation constraints
- **Mountability depends on keeping the embedded server alive.** `pgembed.get_server()` normalizes/creates `pgdata`, de-duplicates per path, then constructs `PostgresServer`; construction initializes PGDATA, starts PostgreSQL, registers `atexit` cleanup, and records the current process handle (`pgembed/src/pgembed/postgres_server.py:43-67`, `pgembed/src/pgembed/postgres_server.py:345-389`). Cleanup is ref-counted and the last handle either stops, deletes, or leaves the server running depending on `cleanup_mode` (`pgembed/src/pgembed/postgres_server.py:262-307`, `pgembed/src/pgembed/postgres_server.py:320-344`). Tests confirm `cleanup_mode=None` leaves the server process running after the context exits, while default/`stop` stops it (`pgembed/tests/test_pgembed.py:178-204`). **Practical implication:** TigerFS is a separate process, so a Pgembed-backed mount must be started while a Python process keeps the `PostgresServer` handle alive, or Pgembed must be started with `cleanup_mode=None` and stopped explicitly later.
- **Unix pgembed is socket-only by default, not TCP.** On non-Windows, Pgembed starts PostgreSQL with `-h ""` and `-k <socket_dir>`, explicitly avoiding IP listeners (`pgembed/src/pgembed/postgres_server.py:165-190`). On Windows it instead uses `127.0.0.1` and a free port (`pgembed/src/pgembed/postgres_server.py:191-202`). `PostmasterInfo.get_uri()` returns `postgresql://postgres:@/<database>?host=<socket_dir>` for Unix sockets and `postgresql://postgres:@<host>:<port>/<database>` for TCP (`pgembed/src/pgembed/utils.py:100-110`). Tests assert the socket file exists and that `get_uri()` contains the selected socket directory unless the path is too long and Pgembed falls back to a runtime socket directory (`pgembed/tests/test_pgembed.py:31-44`, `pgembed/tests/test_pgembed.py:150-167`; socket-dir selection in `pgembed/src/pgembed/utils.py:256-300`).
- **TigerFS/pgx compatibility looks plausible for Pgembed's socket URI.** TigerFS accepts an explicit direct connection string when two mount args are provided (`tigerfs/internal/tigerfs/cmd/mount.go:54-79`, `tigerfs/internal/tigerfs/cmd/mount.go:252-277`), returns explicit connection strings unchanged from `ResolveConnectionString()` (`tigerfs/internal/tigerfs/db/connection.go:63-70`), then resolves password, enforces SSL policy, calls `pgxpool.ParseConfig(connStr)`, creates a pgx pool, and pings (`tigerfs/internal/tigerfs/db/client.go:70-91`, `tigerfs/internal/tigerfs/db/client.go:134-140`). TigerFS' SSL enforcement treats empty URL host, localhost, and hosts beginning with `/` as local and adds `sslmode=disable` if omitted (`tigerfs/internal/tigerfs/db/tls.go:31-47`, `tigerfs/internal/tigerfs/db/tls.go:61-69`, `tigerfs/internal/tigerfs/db/tls.go:132-145`). Pgembed's URI has an empty URL authority plus `?host=/socket/dir`, so it should be exempt from remote TLS enforcement and then parsed by pgx with the query `host` parameter.
- **Pgembed's extension helper does not know `psql_bm25s`.** Pgembed only detects a fixed set of extension packages/shared objects: `pgvector`, `pgvectorscale`, `pgtextsearch`, `pg_search`, and `pg_duckdb` (`pgembed/src/pgembed/__init__.py:23-64`). `PostgresServer.create_extension()` maps only those known extension names, checks `pgembed.has_extension()`, and raises if unavailable (`pgembed/src/pgembed/postgres_server.py:314-340`). **Practical implication:** `pg.create_extension("psql_bm25s")` will not be the activation path unless Pgembed is extended. A raw `CREATE EXTENSION psql_bm25s;` can only work if the extension control/sql/shared-library files are installed into the embedded PostgreSQL installation paths that Pgembed actually runs.

#### 2. TigerFS connection handling and generated SQL/query paths
- **Mount connection flow is generic PostgreSQL over pgx.** `tigerfs mount [CONNECTION] [MOUNTPOINT]` accepts direct `postgres://...` examples and backend refs (`tigerfs/internal/tigerfs/cmd/mount.go:54-79`). Backend refs are resolved to connection strings before mounting (`tigerfs/internal/tigerfs/cmd/mount.go:99-117`). Direct explicit strings are passed through by the connection resolver (`tigerfs/internal/tigerfs/db/connection.go:63-70`) and into `pgxpool.ParseConfig()` (`tigerfs/internal/tigerfs/db/client.go:83-91`). The config fallback path, however, constructs only `postgres://user@host:port/db` from host/port fields (`tigerfs/internal/tigerfs/db/connection.go:89-99`), so Pgembed socket use should be supplied as an explicit URI, e.g. `tigerfs mount "$PGEMBED_URI" /path/to/mount`.
- **Browsing is primary-key/equality/ordering oriented.** Single-row and column reads use ordinary primary-key predicates: `SELECT * FROM <table> WHERE <pk>` and `SELECT <column> FROM <table> WHERE <pk>` (`tigerfs/internal/tigerfs/db/query.go:92-99`, `tigerfs/internal/tigerfs/db/query.go:163-170`). First/last listings select PK columns ordered by PK with `LIMIT` (`tigerfs/internal/tigerfs/db/query.go:515-556`); random sampling uses either `TABLESAMPLE BERNOULLI` or `ORDER BY RANDOM()` (`tigerfs/internal/tigerfs/db/query.go:572-618`).
- **`.filter/` and `.by/` are equality filters, not text search.** Pipeline filters are explicitly modeled as column equality conditions (`tigerfs/internal/tigerfs/db/pipeline.go:46-56`). Generated pipeline SQL emits `WHERE "col" = $n` joined by `AND` (`tigerfs/internal/tigerfs/db/pipeline.go:281-290`, `tigerfs/internal/tigerfs/db/pipeline.go:330-339`). `.filter/<column>/<value>` extends the pipeline with `WithFilter(column, value, false)` (`tigerfs/internal/tigerfs/fuse/filter.go:429-438`), while `.by/` uses indexed columns but still queries equality: `SELECT <pk> FROM <table> WHERE <column> = $1 ORDER BY <pk> LIMIT $2` (`tigerfs/internal/tigerfs/db/indexes.go:360-382`). Composite index navigation generates `col1 = $1 AND col2 = $2 ...` (`tigerfs/internal/tigerfs/db/indexes.go:574-596`). Distinct-value listings use `SELECT DISTINCT <column> ... WHERE <column> IS NOT NULL ORDER BY <column> LIMIT $1`, optionally adding equality filters (`tigerfs/internal/tigerfs/db/indexes.go:245-254`, `tigerfs/internal/tigerfs/db/indexes.go:490-504`).
- **`.order/` is plain SQL column ordering.** TigerFS lists ordinary table columns for ordering (`tigerfs/internal/tigerfs/fuse/order.go:91-131`) and generated SQL uses `ORDER BY "order_col" ASC|DESC NULLS LAST, <pk>` (`tigerfs/internal/tigerfs/db/pipeline.go:384-410`; direct ordered helpers in `tigerfs/internal/tigerfs/db/query.go:638-690`). There is no provision for operator expressions such as `<=> psql_bm25s_order_tokens(...)` in the order path.
- **`.export/` reuses the same ordinary query builders.** Non-pipeline export materializes `SELECT * FROM <table> LIMIT $1` (`tigerfs/internal/tigerfs/db/export.go:26-38`) and serializes CSV/TSV/JSON/YAML (`tigerfs/internal/tigerfs/fuse/export.go:101-111`, `tigerfs/internal/tigerfs/fuse/export.go:236-268`). Pipeline export calls `QueryRowsWithDataPipeline()`, which builds `SELECT <columns|*> FROM <table> [WHERE equality filters] [ORDER BY plain columns/PK/random] [LIMIT]` (`tigerfs/internal/tigerfs/db/pipeline.go:155-206`, `tigerfs/internal/tigerfs/db/pipeline.go:239-304`, `tigerfs/internal/tigerfs/fuse/pipeline_node.go:928-966`).
- **Eliminated hypothesis: TigerFS has a hidden BM25/full-text search hook.** A targeted search under `tigerfs/internal/tigerfs` found no `psql_bm25s`, `bm25`, `to_tsvector`, `tsquery`, `ILIKE`, or `@@@` references. The only `LIKE` uses found during broader reconnaissance were unrelated path-prefix/migration checks, not search/ranking paths. Therefore TigerFS' current default SQL cannot invoke psql_bm25s implicitly.

#### 3. `psql_bm25s` install/index/query surfaces and filesystem-context usefulness
- **`psql_bm25s` is a PostgreSQL extension/index access method.** The current SQL creates an index access method with `CREATE ACCESS METHOD psql_bm25s TYPE INDEX HANDLER psql_bm25s_handler` (`psql_bm25s/sql/psql_bm25s--0.4.14.sql:76-79`), and the control file points to `$libdir/psql_bm25s`, default version `0.4.14`, `relocatable = false` (`psql_bm25s/psql_bm25s.control:1-4`). Installation requires copying release files into PostgreSQL extension/library paths, then `CREATE EXTENSION psql_bm25s;` in the target database; non-`public` schema must be chosen at creation time (`psql_bm25s/README.md:175-198`).
- **Basic use is explicit `CREATE INDEX` plus explicit query functions/operators.** The quick-start creates a table, runs `CREATE INDEX docs_bm25_idx ON docs USING psql_bm25s (body);`, and queries through `psql_bm25s_query('docs_bm25_idx'::regclass, 'apple fruit', 5)` joined back by `ctid` and ordered by returned score (`psql_bm25s/README.md:229-263`). Supported source column types are `int4[]`, `text[]`, `varchar[]`, `text`, and `varchar` (`psql_bm25s/docs/input-types.md:1-17`). Index reloptions include scoring, text processing, consistency, maintenance, and optional shared-preload settings (`psql_bm25s/docs/index-parameters.md:1-36`, `psql_bm25s/docs/index-parameters.md:40-63`, `psql_bm25s/docs/index-parameters.md:83-151`).
- **The exposed retrieval/ranking APIs are not the SQL TigerFS emits.** Canonical exact retrieval is through `psql_bm25s_query_ids(...)` and `psql_bm25s_query_tokens(...)` (`psql_bm25s/docs/query-semantics.md:9-18`; signatures in `psql_bm25s/sql/psql_bm25s--0.4.14.sql:870-887`). Raw-text convenience uses `psql_bm25s_query(...)` and prepared-query helpers (`psql_bm25s/docs/api-reference.md:24-64`, `psql_bm25s/sql/psql_bm25s--0.4.14.sql:922-938`, `psql_bm25s/sql/psql_bm25s--0.4.14.sql:1136-1148`). Operators are `@@`, `@@@`, and `<=>`, with opclasses for text arrays, varchar arrays, scalar text/varchar, and int4 arrays (`psql_bm25s/docs/api-reference.md:214-240`, `psql_bm25s/sql/psql_bm25s--0.4.14.sql:763-868`, `psql_bm25s/sql/psql_bm25s--0.4.14.sql:1780-1814`). TigerFS' generated SQL uses `=`, `ORDER BY <column>`, `ORDER BY <pk>`, `ORDER BY RANDOM()`, and `SELECT *`; it does not emit these psql_bm25s functions/operators.
- **Eliminated hypothesis: ordinary `LIKE`/`ILIKE`/`ORDER BY column` will use BM25 automatically.** `psql_bm25s` docs say `<=>` is true BM25 ordering only when PostgreSQL chooses a real `psql_bm25s` index scan, and recommend `psql_bm25s_query_tokens(...)` or `psql_bm25s_query_ids(...)` for the clearest exact contract (`psql_bm25s/docs/api-reference.md:222-240`). The SQL opclasses expose `@@`, `@@@`, and `<=>`, not `LIKE` or `ILIKE` (`psql_bm25s/sql/psql_bm25s--0.4.14.sql:841-868`, `psql_bm25s/sql/psql_bm25s--0.4.14.sql:1802-1814`). The docs also warn that raw scalar text operators outside a real index scan do not silently discover hidden index reloptions (`psql_bm25s/docs/api-reference.md:230-238`, `psql_bm25s/docs/index-parameters.md:58-63`).
- **Preload is optional for basic search but not sufficient to affect TigerFS.** Shared-preload settings are documented as optional/background-residency features that do not change scoring or consistency semantics (`psql_bm25s/docs/index-parameters.md:126-170`). Even if `shared_preload_libraries = 'psql_bm25s'` is configured in embedded PostgreSQL, TigerFS' default filesystem navigation still will not call BM25 APIs.

#### Practical conclusions
- **Yes, Pgembed can likely be mounted through TigerFS as a PostgreSQL backend** if the Pgembed server is already running and TigerFS receives the Pgembed `get_uri()` string explicitly. On Unix this is a socket URI (`postgresql://postgres:@/dbname?host=/socket/dir`); TigerFS uses pgx and should parse it after adding local `sslmode=disable`. Keep the Pgembed server alive for the lifetime of the mount, preferably by holding the Python server handle open or using `cleanup_mode=None` and cleaning up deliberately.
- **`psql_bm25s` can coexist in the mounted database only if it is installed into the embedded PostgreSQL distribution and `CREATE EXTENSION psql_bm25s;` succeeds.** Pgembed's built-in extension discovery/helper does not currently include it, so installation/activation would be manual or require Pgembed packaging changes.
- **`psql_bm25s` will not usefully affect TigerFS default browsing/filter/order/export behavior today.** TigerFS does not generate psql_bm25s query functions, `@@`, `@@@`, or `<=>`; `.filter/`/`.by/` are equality filters, `.order/` is plain column sorting, and `.export/` is `SELECT *`/pipeline export. Any useful BM25 behavior would require a new TigerFS capability/query path (for example `.search/<index>/<query>/.first/N/` implemented with `psql_bm25s_query(...)` or explicit `<=>` ordering) or a user-created database view/function that exposes BM25 results as ordinary rows TigerFS can browse.

## Root Cause
There is no bug so much as a layering mismatch:

```text
TigerFS filesystem view
  -> generated ordinary PostgreSQL SQL over pgx
  -> Pgembed's embedded PostgreSQL server
  -> optional PostgreSQL extensions/indexes inside that server
```

Pgembed is mountable because it runs a real PostgreSQL server and exposes a PostgreSQL URI. On Unix, it starts socket-only with `-h ""` and `-k <socket_dir>` (`pgembed/src/pgembed/postgres_server.py:188-211`), and the URI is `postgresql://postgres:@/<database>?host=<socket_dir>` (`pgembed/src/pgembed/utils.py:100-110`). TigerFS accepts explicit connection strings and parses them via pgx/pgxpool (`tigerfs/internal/tigerfs/db/client.go:83-91`).

However, `psql_bm25s` is a PostgreSQL index access method and SQL API, not a FUSE/TigerFS plugin. It defines a PostgreSQL access method (`psql_bm25s/sql/psql_bm25s--0.4.14.sql:91`) and is used through `CREATE EXTENSION`, `CREATE INDEX ... USING psql_bm25s`, `psql_bm25s_query*`, `@@`, `@@@`, and `<=>`. TigerFS current default paths generate equality predicates, plain ordering, primary-key ordering, random ordering, and `SELECT *` exports, not BM25-specific SQL (`tigerfs/internal/tigerfs/db/pipeline.go:281-290`, `tigerfs/internal/tigerfs/db/indexes.go:374-378`, `tigerfs/internal/tigerfs/db/export.go:32-35`). Therefore a BM25 index will not automatically affect TigerFS `.filter/`, `.by/`, `.order/`, `ls`, or `.export/` behavior.

A second practical constraint is Pgembed extension packaging: Pgembed's helper registry does not include `psql_bm25s` (`pgembed/src/pgembed/__init__.py:23-64`), and `PostgresServer.create_extension()` only allows known extensions after `has_extension()` (`pgembed/src/pgembed/postgres_server.py:314-344`). So `psql_bm25s` must first be installed into Pgembed's embedded PostgreSQL installation manually/build-time, and activated with raw SQL or Pgembed registry changes.

## Recommendations
1. **Mount Pgembed through TigerFS as a normal PostgreSQL backend:** start Pgembed, keep the server handle alive, and run TigerFS with the explicit URI from `pg.get_uri("dbname")`:
   ```bash
   tigerfs mount "postgresql://postgres:@/dbname?host=/path/to/socket_dir" /mnt/pgembed
   ```
   On Windows, expect a `127.0.0.1:<port>` URI instead of a Unix socket URI.
2. **Keep Pgembed alive for the mount lifetime:** do not let the Python context/handle exit with default cleanup while TigerFS is mounted. Use a long-lived Python process or `cleanup_mode=None` with deliberate shutdown.
3. **Install `psql_bm25s` into the embedded PostgreSQL before use:** build/copy compatible artifacts into Pgembed's PostgreSQL layout, including `lib/postgresql/psql_bm25s.so`, `share/postgresql/extension/psql_bm25s.control`, and versioned SQL files, then run raw SQL such as `CREATE EXTENSION psql_bm25s;`. Verify PostgreSQL major version, platform ABI, and dependencies.
4. **Do not expect automatic BM25 filesystem search:** TigerFS default `.filter/`, `.by/`, `.order/`, and `.export/` paths will not invoke `psql_bm25s` operators/functions.
5. **If BM25 should be visible through TigerFS, add an explicit integration:** either implement a TigerFS BM25-aware path that generates `psql_bm25s_query(...)` / `<=>` SQL, or materialize/search results into ordinary tables/views that TigerFS can browse.

## Preventive Measures
- Document the layered integration model: TigerFS mounts PostgreSQL endpoints; PostgreSQL extensions affect SQL only when TigerFS or the user emits the relevant SQL.
- Add a Pgembed extension compatibility checklist for new native extensions: PostgreSQL version, control/SQL files, shared library path, preload needs, ABI/dependencies, and registry/helper support.
- If TigerFS adds search features, write tests proving the generated SQL uses `psql_bm25s` functions/operators and that planner/index behavior is exercised against a real `psql_bm25s` index.
- Add an example script demonstrating the safe Pgembed → TigerFS mount lifecycle, including how to keep the Pgembed server alive and pass the socket URI.
